# Result Format

The actual schema enforced by this codebase — not an idealized one. If you're writing a new wrapper (`04_Writing_Experiment_Scripts.md`) or trying to explain a result to a user, use these field names, not invented ones like `"metadata"` or `"artifacts"` (this system does not have those).

## What a script must return

Enforced by `core/runner.py::_parse_and_validate_result` — anything that doesn't satisfy this will raise `RuntimeError`, not a graceful `status: "failed"`:

- Must be a JSON-serializable `dict`.
- Must contain `"status"`, and its value must be exactly `"success"` or `"failed"` — nothing else. (There used to be a `"needs_retry"` value in some wrappers; that was a bug, since the runner never accepted it. Don't reintroduce it.)
- If `"status"` is `"failed"`, an `"error"` key is required.

Everything else in the returned dict is convention, not enforced by the runner — but `tools/lab_tool.py` looks for specific keys when it stores the result:

```python
results_data = result_dict.get("results") or result_dict.get("data", {})
arrays       = result_dict.get("arrays", {})     # not populated by any current script
plots        = result_dict.get("plots", [])
```

## Field Reference

| Field | Where it comes from | Notes |
|---|---|---|
| `status` | required, `"success"` \| `"failed"` | Enforced by the runner |
| `error` | required if `status == "failed"` | Human-readable summary; per-qubit detail usually lives one level down in `results` |
| `results` (or `data`) | script-specific | The four multi-qubit wrappers use `results: {qubit_name: {...}}`; the single-qubit `qblox_qubit_spectroscopy` uses a flat `data: {...}` dict of named scalars/arrays — **the two shapes are not interchangeable**, check which one a given experiment uses (`03_Experiment_API.md`) |
| `plots` | script-specific, optional | List of `{"name": str, "format": "plotly" \| "png" \| "base64", "data": ...}`. For `"plotly"`, `data` is `{"data": [...traces], "layout": {...}}`. For `"png"`/`"base64"`, `data` is a base64-encoded string of the PNG bytes (build it with `png_plot_entry()` from `_ising_utils.py`, don't hand-roll it) |
| `arrays` | — | Part of the schema (`core/models.py::ExperimentResult.arrays`) but **no script currently populates it**. Numeric arrays instead live nested inside `results`/`data` (e.g. `results[qubit]["data"]["frequency_hz"]`). `lab(action="get_array"/"list_arrays"/"get_stats")` will return nothing for any experiment today — don't rely on it; read the arrays out of `results`/`data` directly, or `history_show` |
| `accepted` | convention (all qblox wrappers) | Overall pass/fail across all qubits in the call; independent of `status` in principle but currently always matches it |
| `update_applied` | convention (wrappers with `apply_update`) | Whether the fitted value was actually written back to device config this call |
| `config_saved` | convention (wrappers with `apply_update`) | `null` unless `update_applied` is true. When present: `{"device_config": path, "hardware_config": path, "backups": {path: backup_path_or_null}}` — see `save_device_config()` in `_qblox_runtime.py`. This is the actual disk write; `update_applied` alone does not guarantee persistence (see below) |
| `tuid` | via `common_payload()` | Qblox's internal timestamped unique ID for the underlying dataset — different from QCA's own `experiment_id` |

**Persistence gotcha**: `node.post_run()` (the qblox_scheduler calibration node method) only mutates the in-memory `quantum_device`/`hardware_configuration` Python objects — it never writes to disk on its own. Since every `run_experiment` call is a fresh subprocess (`07_Best_Practices.md`), an in-memory-only update is discarded the instant the subprocess exits. Every wrapper that supports `apply_update` therefore calls `save_device_config(hw_agent)` immediately after a successful `post_run()` to actually persist the change — check `config_saved` in the result, not just `update_applied`, to confirm a write really reached disk. `save_device_config()` backs up the previous version of both config files (timestamped `.bak.json`) before overwriting.

## What actually gets persisted

`tools/lab_tool.py::_run_experiment` wraps the raw dict above into an `ExperimentResult` (`core/models.py`) before storing it:

```python
id: str            # "<UTC timestamp>_<experiment_name>", generated by QCA, not the script
type: str           # experiment_name
timestamp: str      # ISO 8601 UTC
status: str
target: Optional[str]   # from params.get("target") — most qblox wrappers don't use this key, so usually None
params: dict        # the exact params the caller passed
results: dict       # results_data from above
arrays: dict        # always {} today, see above
plots: list
notes: str
file_path: str      # set on load, not on save
```

This is saved as one HDF5 file per run under `data/experiments/YYYY/MM/DD/HHMMSS_<type>.h5`, indexed in `data/index.db` (SQLite). `lab(action="history_show", experiment_id=...)` returns `ExperimentResult.to_dict()` verbatim — that's the most reliable way to retrieve everything about a past run, including nested raw data buried in `results`/`data`, since the more "structured" `get_array`/`get_stats` actions don't work (see above).

A separate, real-time text log per run — `data/<experiment_id>/output.log` — captures redirected stderr while the experiment is running (see `04_Writing_Experiment_Scripts.md`'s logging section). This is not part of the JSON result; it's for watching progress or debugging a crash.

## Minimal Valid Examples

Success:
```json
{"status": "success", "results": {"q1": {"accepted": true, "resonance_frequency_hz": 5687000000.0}}, "plots": []}
```

Failure:
```json
{"status": "failed", "error": "q1: fit_failed, low_r_squared"}
```

Anything missing `status`, or with `status` set to anything other than these two strings, is a bug in the script — not a valid "in-between" result.
